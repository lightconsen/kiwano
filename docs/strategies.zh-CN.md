# 策略与限额

每个 Agent 的路由是一个有序候选队列——绑定到它的供应商们。**策略**决定
下一个请求由哪个候选服务;队列的其余部分是本次尝试中途失败时的重放顺序。
本页覆盖策略、花费限额,以及订阅计划的用量读取。

## 六种策略

| 策略 | 选择逻辑 | 说明 |
| --- | --- | --- |
| `single` | 永远是主供应商。 | 默认值。一个供应商,没有重放尾巴——但 Agent 超过自身花费限额时,任何策略(包括 `single`)都会拒绝。 |
| `failover` | 按优先级取第一个熔断器可用的候选。 | 所有熔断器都断开时,仍会尝试主供应商。429 设置供应商自己声明的短暂暂停;500 计入熔断器。 |
| `roundrobin` | 加权轮转——**按会话**。 | 一段对话保持其供应商,让它已付费的上游 prompt cache 继续命中;新会话按权重挑选;只有粘住的候选不可用时才重新分配。 |
| `timewindow` | 本地 `HH:MM` 窗口(支持跨午夜)包含当前时间的候选。 | 无命中时回退主供应商。会话粘性与 `roundrobin` 相同。 |
| `quota` | 主供应商当日用量(请求数或 token 数,读自用量聚合)超过策略配置里的阈值后,沉到备份——即 failover 语义。 | 同样的会话粘性:切换发生在*下一段*对话。 |
| `least-busy` | 熔断器可用、当前在途请求数最少的候选。 | 会话先排干(与其他粘性策略一致);优先级顺序打破平局。 |

两条跨策略成立的性质:

- **一段对话保持其供应商。** 在粘性策略(`roundrobin`、`timewindow`、
  `quota`)下,切换落在*下一段*对话;已在运行的对话在原地结束,而不是
  重建一个它的供应商已经收过费的 prompt cache。不带会话标识的请求照旧
  重新挑选。
- **失败被重放,而不是被退回。** 除 `single` 外的任何策略,中途失败的
  请求会沿队列对下一个候选重放,而不是作为错误交还给你的 Agent。

## 花费限额(Agent 限额)

每个 Agent 可以按周期设限额——`day`、`weekly`、`monthly`、`yearly` 或
`all`——每个限额由数额和单位组成:请求数(`requests`)、万 token 块
(`wan_tokens`),或一个 **ISO 货币代码**。

币种规则是刻意的:限额以该 Agent 的供应商实际计费的币种计,而不是你的
显示偏好币种。供应商用别的币种计费时,它的花费先按 Hub 汇率*折算*再计入
限额——限额本身永不折算。到达限额后,该 Agent 的新请求被拒绝,理由在 UI
可见,任何策略下都一样。

## 用量数字从哪来

- **计量用量**来自网关自己的请求记账——每条请求的 token 与成本,归属到
  服务它的供应商。
- **订阅计划配额**(发布"你的计划用了多少"的订阅)通过*plan query* 从
  供应商自己的端点读取。少数目录条目自带查询模板(Kimi、智谱个人与团队、
  MiniMax、ZenMux、OpenCode Go、火山引擎);结果缓存五分钟,可强制刷新。
  一个供应商可以*按计划计费*却不支持 plan query——查询模板才是配额环
  有意义的前提。

## 成本显示,以及唯一发生折算的地方

成本按各供应商计费的币种记录,并在所有地方按该币种显示——唯独
**Dashboard** 使用你的偏好显示币种,由 Hub 汇率完成折算。供应商自己的
行永远不会显示折算后的数字;行上是 ¥,就意味着供应商以 ¥ 计费。

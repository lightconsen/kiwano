**この分離を宣言するバージョン。** 0.2.13 で app と CLI はゲートウェイのクライアントに
なりました — 読み書きは管理面の API を通り、共有データベースに書き込むのはゲートウェイ
だけ、`kiwano reload` は削除。これは破壊的変更でありながらパッチ番号で出てしまいました。
0.3.0 はその線を引き直す場所であり、マシンをまたぐ話の残り半分が入った版でもあります。

### 追加

- **データプレーンは loopback の外でもリッスンできます: `KIWANO_DATA_ADDR`。** 未設定なら
  `127.0.0.1` で、これは今日のすべてのインストールと同じです。つまり求めなければ何も変わり
  ません。プライベートなアドレスを設定すれば、**別のマシン**のエージェントがこのマシンの
  ゲートウェイに到達できます — これは 0.2.13 のリリースノートが説明しながら実現できて
  いなかったことです。2 台目から実行したテイクオーバーは遠隔側のアドレスを書き、遠隔側は
  自分の loopback でリッスンしていたため、書かれたアドレスは何も応答しませんでした。

- **`KIWANO_DATA_ALLOW_ANY`**。どこからでも到達できるアドレスにはこれが要ります。プライベート
  範囲の判定は管理プレーンと同じ規則です(RFC1918、loopback、リンクローカル、tailnet が使う
  `100.64/10`)。このスイッチが**管理プレーンのものと別**なのは意図的です。あちらを流れるのは
  資格情報、このリスナーを流れるのはリクエストとレスポンスそのもの。前者をネットワークに
  晒すと決めた人が、それによって後者も晒すと決めたことにはなりません。

- **`/status` が `data_port` とともに `data_host` を報告します。** クライアントは以前、
  ゲートウェイがどこにあるかについての自分の思い込みからエージェントの URL を組み立てて
  いました。二つのプレーンが同じインターフェースにないときは必ず間違う —— そして上のバグは
  まさにそうして生まれました。

### 修正

- **別のマシンからのテイクオーバーは、応答するアドレスをエージェントに指すようになりました。**
  上の `KIWANO_DATA_ADDR` を参照。これがユーザーに見える半分で、エージェントを 1 つ
  テイクオーバーしてリクエストを送れば確認できます。

- **daemon の解析可能な ready 行が、実際に束縛したアドレスを名乗るようになりました。**
  `127.0.0.1` と書いていたのは、かつてそれが唯一の可能性だったからで、そうでなくなった後も
  書き続けていました。あの行は起動したプロセスに解析されるためにあり、間違ったアドレスを
  名乗るのは何も出さないより悪いことです。

### 変更

- **マシンをまたぐ設定にページができました:**
  [ゲートウェイを別のマシンに置く](https://kiwano.cc/docs/ja/remote-gateway/) — 二つの
  プレーン、5 つの環境変数、管理トークンの入手先、そして平文転送に伴うデプロイ要件
  (プライベートネットワークか VPN、公開アドレスには置かない)。`kiwano` の CLI リファレンス
  と新ページは相互にリンクし、README も同様です。

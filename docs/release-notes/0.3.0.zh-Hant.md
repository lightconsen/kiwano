**宣告這次分離的版本。** 0.2.13 讓 app 與 CLI 成了閘道的用戶端 —— 讀寫都經它的
管理面 API、共享庫唯一的寫入者是閘道、`kiwano reload` 刪掉了。那是一次破壞性變更,卻
裝在了一個 patch 號裡;0.3.0 是把這條線畫清楚的地方,跨機故事的另一半也在這裡落地。

### 新增

- **資料面可以監聽 loopback 之外:`KIWANO_DATA_ADDR`。** 不設就是 `127.0.0.1`,也就是今天
  每一個安裝的樣子,所以你不要求就什麼都不變。把它設成一個私有位址,**另一台機器上**的
  Agent 就能連到這台機器上的閘道 —— 這正是 0.2.13 的發行說明描述過、卻沒做到的事:從第二台
  機器發起的接管寫下了遠端那台的位址,而那台機器只在自己的 loopback 上聽,於是寫下去的
  位址無人應答。

- **`KIWANO_DATA_ALLOW_ANY`**,誰都能連到的位址需要它。私有網段的判據和管理面用的是同一條
  (RFC1918、loopback、連結本地,以及 tailnet 用的 `100.64/10`)。這個開關**與管理的那個
  分開**是刻意的:一個走的是憑證,而這個監聽上走的是請求與回應本身;決定讓前者面對網路的
  人,並沒有因此決定後者也可以。

- **`/status` 在 `data_port` 之外一併報 `data_host`。** 用戶端過去按自己對「閘道在哪」的想法
  去拼 Agent 的 URL,只要兩個平面不在同一個介面上就必然拼錯 —— 而上面那個 bug 正是這樣來的。

### 修正

- **從另一台機器發起的接管,現在把 Agent 指向一個會應答的位址。** 見上面的
  `KIWANO_DATA_ADDR`;這是它使用者可見的那一半,接管一個 Agent 再發一個請求即可驗證。

- **daemon 那行可解析的 ready 現在報的是它真正綁定的位址。** 它寫著 `127.0.0.1`,因為那曾
  是唯一的可能,而在不再是之後它還在這麼寫。那行的意義就是被啟動它的行程解析,所以報一個
  錯的位址比不印更糟。

### 變更

- **跨機設定有了一頁文件:** [把閘道放在另一台機器上](https://kiwano.cc/docs/zh-Hant/remote-gateway/)
  —— 兩個平面、五個環境變數、管理 token 從哪兒來,以及明文傳輸帶來的那條部署要求:私有網路
  或 VPN,絕不放在公網位址上。`kiwano` 的 CLI 參考與新頁互相連結,README 也是。
